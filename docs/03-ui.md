# UI

## Layout

- Top: a one-row agent tab strip. One tab per registered agent-backend
  strategy, in registration order; exactly one tab is always selected and
  there is no `All` tab. The selection defaults to the first registered agent
  on every start and is not persisted.
- Middle: the two-column browser (Projects left, Sessions right) starts below
  the strip, with a one-cell gap. There is no focus tab row; the focused pane
  is shown by its highlighted border and by the status badge.
- Bottom: status bar and keyboard hints.

### Agent Tabs as Working Context

The registered tabs are `Claude` then `Pi`. Both remain selectable even when empty.

The selected tab scopes the whole browser: the Projects column lists only
directories with at least one session of the selected agent (the synthetic
`Open Here` row is always present), and the Sessions column shows only that
agent's sessions of the current project. A directory with sessions from
several agents appears once under each of those agents' tabs, each view
showing only its own sessions. Enter, `n`, and `Open Here` start a new session
of the selected tab's agent.

On startup, Cowboy discovers the default agent's projects, sorts them by path,
selects the first real project, and loads only that project's sessions in the
background. Other projects load when first selected, and revisits reuse valid
results in memory. `Open Here` does not scan session history. The other agent's
project catalog is discovered on its first visit. After a mutation or return
from an agent, Cowboy refreshes the affected project and updates membership as
needed rather than reloading all session summaries.

When switching tabs, the same working directory stays selected if it exists
under the new tab; otherwise Cowboy selects the first project, or `Open Here`
if the list is empty. Session selection resets to the first row and the search
query is preserved.

Token usage does not add a third primary column in the first implementation.
The existing two-column layout remains the default to preserve narrow terminal
behavior.

### Sessions Pane Title

The tab strip is the single source of truth for the active agent, so the
Sessions pane title carries only the search query:

- `Sessions` — no search query
- `Sessions / query` — searching only the selected project's sessions, never other projects

The pane shows an animated `Loading sessions…` until the selected project's
sessions are available, and then applies any active query. `No sessions` means
there are no sessions to display; `No matching sessions` means the project has
sessions but none match the query. A failed load shows an error instead of an
empty state. Switch away and back to retry the failed project load.

### Duplicate Project Names

Project rows normally display the project directory name only. When two or more
loaded projects have the same directory name, each colliding row displays its
direct parent directory and project directory, for a maximum of two path
segments. For example, `/workspace/team-a/api` and `/workspace/team-b/api` are
shown as `team-a/api` and `team-b/api`. Projects whose directory names are
unique keep the shorter single-segment label, such as `api`.

### Project and Session Row Usage

A project row shows its name and the selected agent's loaded session count,
for example `cowboy (8)`. If its sessions are not loaded or there are none,
it shows only the name. Project rows do not calculate or display token totals.
The synthetic `Open Here` row remains unchanged.

A session row shows reported cost when available, otherwise estimated cost.
If neither is available, it shows neither cost nor a token count. Open
`Session Info` with `i` to see the selected session's token usage.

### Token Total Definition

The session total uses the following four-component sum:

`input tokens + output tokens + cache creation tokens + cache read tokens`

All values go through the same compact formatter: raw integers below 1 000, one
decimal `K` below 1 000 000, and one decimal `M` at or above 1 000 000.

### Session Info Token Display

The Session Info modal shows the selected session's token breakdown:

- Input Tokens
- Output Tokens
- Cache Write
- Cache Read
- Total Tokens (sum of all four categories, same compact formatter)

When usage data is unavailable, the modal shows `Token Usage: Unknown`.

## Popups

- Session Info
- Rename
- Delete Confirmation: `Ctrl+D` opens the dialog; `Enter`, `y`, or a second
  `Ctrl+D` confirms; `q`, `Esc`, or `n` cancels.

Session Info should include detailed token usage and estimated cost when local
session `usage` data is available:

- Model
- Input tokens
- Output tokens
- Cache creation tokens
- Cache read tokens
- Server-side tool usage, if present
- Pi-reported cost takes precedence over an estimate: rows show `$X.XX`; details show `Cost: $X.XXXX` with `(reported by provider)` only when all contributing records are provider-origin, otherwise `(reported by pi)`.
- Without reported cost, a known model and usage yield `Est. Cost` with the estimate note; otherwise the row falls back to token usage when available.

Token values in Session Info use the same compact display as the session list:
raw integers below `1_000`, one decimal `K` below `1_000_000`, and one decimal
`M` at or above `1_000_000`.

## Primary Actions

Enter in Projects: New Session in the selected project, inheriting the parent process environment
Enter on `Open Here`: New Session in the current working directory without creating a project settings file
Enter in Sessions: Resume the selected session, inheriting the parent process environment
`[` / `]` / `Tab` / `←` / `→`: switch focus between Projects and Sessions
a Cycle the agent tab selection in registration order, wrapping to the first.
  With a single registered agent this is a no-op that still reports the active
  agent in the status bar.
n New Session in the selected project from the Sessions pane
i Info
r Rename
Ctrl+D Delete
  - in `Projects`: delete the selected project and all discovered sessions under it
  - in `Sessions`: delete the selected session only
  - `Ctrl+D` in the confirmation dialog confirms deletion
  - after confirmation, deletion runs in the background and the status bar
    changes to `Deleting`; the lists remain visible until a successful refresh
q / Esc Quit
/ Search

### Deletion In Progress

After a delete confirmation is accepted, the TUI remains visible and responsive
while the filesystem operation runs. The status badge identifies the deletion
target and asks the user to wait. The key-hint row becomes a waiting-only hint:
normal navigation and action hints are not shown.

During this state, all application keyboard actions are ignored. In particular,
`q` and `Ctrl-C` do not exit; they reaffirm that deletion is in progress. `Esc`
is also disabled and does not exit. This prevents a second delete, rename,
launch, or focus change from acting on stale list state.
Once the worker finishes, normal shortcuts return. A successful completion
refreshes the project list and shows the normal delete success status; a failed
completion keeps the current list and shows an error toast.

## Key Hints

- Bottom key hints change with the active pane
- In `Projects`, the hint row shows `Enter New Session`; selecting `Open Here` uses the current working directory
- In `Sessions`, the hint row shows `Enter Resume`
- In `Projects`, the hint row shows `Ctrl+D Delete Project`
- In `Sessions`, the hint row shows `Ctrl+D Delete Session`
